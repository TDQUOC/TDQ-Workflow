Section 2

Kinh Tế Token & Thác Nước Carry-Cost (Token Economics)

Phân tích định lượng sự tiêu hao ngữ cảnh trong các phiên làm việc dài (multi-turn agent session). Chứng minh tại sao việc mang vác tài liệu tĩnh làm suy giảm năng lực suy luận của LLM.

Thác Nước Tích Lũy Carry-Cost Qua 50 Tool Calls
Tổng số token API phải tái đọc (Cumulative Re-read Tokens)

Hội Chứng "Lost In The Middle" Do Nạp Thừa Ngữ Cảnh

Mỗi tool call của Agent (Read, Edit, Bash, Grep) trong Claude Code là một API turn độc lập. Toàn bộ lịch sử hội thoại, bao gồm toàn bộ instruction tĩnh nạp ở đầu phiên, bị gửi lại máy chủ và đọc lại từ đầu.

Công thức Carry-Cost thực tế:
Nạp tĩnh 9.000 tokens instruction tĩnh × 50 tool calls = 450.000 tokens lãng phí.
Chỉ cần cắt giảm xuống 1.300 tokens (500 tokens Karpathy + 800 tokens TDQ essentials), chi phí giảm ngay còn 65.000 tokens (giảm 85.5%).

Quan trọng hơn chi phí tài chính: Khi context window bị nhồi nhét 10.000 tokens tài liệu tĩnh, sự chú ý (attention weight) của mô hình bị suy giảm nghiêm trọng. Mô hình dễ bị "quên" các điều kiện nghiệp vụ cốt lõi nằm ở giữa đoạn hội thoại, dẫn đến lỗi code hời hợt hoặc làm sai yêu cầu ban đầu.

1. Think Before Coding (Tư Duy Trước Khi Viết Code)

Trị bệnh: Tự tiện đoán mò
"The models make wrong assumptions on your behalf and just run along with them without checking. They don't manage their confusion, don't seek clarifications, don't surface inconsistencies, don't present tradeoffs, don't push back when they should." — Andrej Karpathy (README.md, dòng 15)

Bài học cho TDQ: Quy trình phỏng vấn `tdq-intake` hiện tại rất nặng tính khảo sát thụ động (hỏi đủ 7 câu trắc nghiệm). Cần chuyển hóa thành thái độ chủ động phản biện (Push Back) và trình bày đánh đổi (Surface Tradeoffs) kèm ước lượng thời gian.

❌ LLM Hành Xử Sai (Âm Thầm Đoán Mò - EXAMPLES.md:15-30) Sai lầm điển hình 
# Yêu cầu: "Add a feature to export user data"
# LLM tự tiện xuất TẤT CẢ user ra file JSON local, không phân trang, không bảo mật
def export_users(format='json'):
    users = User.query.all()
    if format == 'json':
        with open('users.json', 'w') as f:
            json.dump([u.to_dict() for u in users], f)
    # Lỗi: Giả định phạm vi, tự chọn vị trí file, lộ dữ liệu nhạy cảm!
✅ Chuẩn Karpathy & TDQ Đề Xuất (Bề Mặt Hóa Đánh Đổi - EXAMPLES.md:41-55) Hành vi chuẩn 
Before implementing, I need to clarify:
1. Scope: Export all users or filtered subset? (privacy implications)
2. Format: Download file in browser vs background job with email vs API endpoint?
3. Tradeoffs: Simplest approach is a paginated JSON endpoint (1 hour).
             File generation with email takes 3 hours.
What's your preference?

2. Simplicity First (Đơn Giản Là Trên Hết)

Trị bệnh: Hội chứng Over-Engineering
"They really like to overcomplicate code and APIs, bloat abstractions, don't clean up dead code... implement a bloated construction over 1000 lines when 100 would do... No abstractions for single-use code." — Andrej Karpathy (README.md:17, CLAUDE.md:22)

Bài học cho TDQ: `clean-code.md` của TDQ cổ súy mạnh mẽ cho OCP và DIP, khiến Agent dễ lạm dụng Design Pattern cho các bài toán chỉ dùng một lần. Cần bổ sung nguyên lý: "Luật YAGNI đứng trên OCP/DIP: Nếu chỉ có 1 trường hợp sử dụng, cấm dựng Strategy Pattern hoặc Abstract Class!"

❌ LLM Hành Xử Sai (Dựng Cấu Trúc Khủng Cho Việc Đơn Giản - EXAMPLES.md:105-145) Over-engineering 
# Yêu cầu: "Add a function to calculate discount"
class DiscountStrategy(ABC): ...
class PercentageDiscount(DiscountStrategy): ...
class FixedDiscount(DiscountStrategy): ...
class DiscountConfig: ...
class DiscountCalculator:
    # 40 dòng code và 4 class chỉ để tính số tiền giảm giá!
✅ Chuẩn Karpathy & TDQ Đề Xuất (Hàm Phẳng Tinh Gọn - EXAMPLES.md:152) Tối giản thực chiến 
def calculate_discount(amount: float, percent: float) -> float:
    """Calculate discount amount. percent should be 0-100."""
    return amount * (percent / 100)

3. Surgical Changes (Can Thiệp Chính Xác Như Phẫu Thuật)

Trị bệnh: Drive-by Refactoring & Style Drift
"Touch only what you must. Clean up only your own mess... Don't 'improve' adjacent code, comments, or formatting. Don't refactor things that aren't broken. Every changed line should trace directly to the user's request." — Andrej Karpathy (CLAUDE.md:31-43)

Bài học cho TDQ: Mã `ANTI-6` của TDQ chỉ mới chặn việc sửa ngoài file. Khi vào đúng file, Agent TDQ vẫn hay "tiện tay" format lại dấu nháy đơn/kép hoặc sửa comment lân cận. Cần đưa nguyên tắc Traceability Test (Mọi dòng diff phải giải thích được bằng một yêu cầu) vào `edit_gate`.

4. Goal-Driven Execution (Hành Động Hướng Mục Tiêu Đo Được)

Trị bệnh: Hành động theo cảm tính
"LLMs are exceptionally good at looping until they meet specific goals... Don't tell it what to do, give it success criteria and watch it go." — Andrej Karpathy (README.md:135)

Bài học cho TDQ: TDQ đã làm rất xuất sắc với TDD Red-Green và bộ mã cấm `ANTI-1` (chống Fake Red), `ANTI-2` (chống Blind Assertion). Điểm cần tối ưu hóa là biến các task trong plan thành công thức tự động hóa: [Mục tiêu] -> verify: [Lệnh test cụ thể] để Agent tự lặp mà không cần người dùng can thiệp từng bước.

✅ Chuẩn Hóa Kế Hoạch Theo Mô Hình Lặp Hướng Đích (Goal-Driven Loop) Tự động hóa cao 
Task T1: Tái hiện lỗi duplicate score sorting
  - Verify RED: python -m unittest tests/test_sort.py -k test_duplicate -> Phải FAIL vì thứ tự bất định
Task T2: Sửa thuật toán sắp xếp ổn định (Stable Sort)
  - Verify GREEN: python -m unittest tests/test_sort.py -k test_duplicate -> PASS 100%
Task T3: Kiểm tra hồi quy toàn diện
  - Verify GREEN: python scripts/tdq_test.py vung-cham --silent -> PASS 100%
Section 4

Bản Đồ Ma Sát Nhận Thức (Cognitive Friction Analysis)

Mổ xẻ các điểm nghẽn thực tế nơi Agent TDQ thường xuyên bị bế tắc nhận thức hoặc sinh ra hành vi xin lỗi quanh co.

Giai Đoạn Pipeline Điểm Đỏ Ma Sát Nhận Thức (Friction Hotspot) Hậu Quả Đối Với Agent Giải Pháp Tháo Gỡ Tâm Lý (Học Từ Karpathy)
1. Intake & Phỏng Vấn Khảo sát 2 tầng quá nhiều câu hỏi máy móc; cấm đoán mò nhưng không hướng dẫn cách phản biện. Agent tập trung tạo bảng hỏi trắc nghiệm dài dòng thay vì nhìn ra điểm phi lý của yêu cầu. Chuyển thành 1-Turn Surface Tradeoffs: Nêu rõ 2-3 kịch bản, ước lượng công sức và chủ động đề xuất giải pháp đơn giản hơn.
2. Lập Kế Hoạch (Plan) Bắt buộc khai báo quá nhiều trường dữ liệu phụ (eNm, Chạm, Cần, Hub, Luật file nóng). Agent tốn 40% dung lượng suy luận chỉ để căn chỉnh format plan, dễ quên đánh dấu checkbox `[~]`. Quy chuẩn hóa plan theo công thức Karpathy: [Step] -> verify: [check]. Mọi trường nâng cao chỉ nạp khi có điều kiện.
3. Viết Mã (Implement) Bị Hook `edit_gate` chặn với lỗi `[TDQ:TICK]` hoặc `streak >= 3`. Agent hoảng sợ, viết lời xin lỗi dài dòng trong chat, thử lách qua shell, đốt thêm turn vô ích. Bổ sung Mental Model "Bác sĩ phẫu thuật": giải thích rõ ràng nhát dao cần rạch thay vì chỉ phạt bằng exit code.
4. Kiểm Định (QC) Log kiểm thử thô in tràn lan hàng trăm dòng vào chat context. Làm loãng context window, khiến Agent bị "Lost in the middle" khi bước sang phase báo cáo. Đã giải quyết ở v0.70.0 bằng Silent CLI (`--silent`): Log thô ra file đĩa, chat chỉ in đúng 2 dòng tóm tắt và lỗi chính.
