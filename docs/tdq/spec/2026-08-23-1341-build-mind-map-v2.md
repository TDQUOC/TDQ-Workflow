## 1. Mục tiêu & phạm vi

- Mục tiêu: viết một tài liệu thiết kế đủ chi tiết để một request sau có thể build lớp sơ đồ
  giải thuật v2 mà không phải quyết định thêm điều gì. Đủ chi tiết nghĩa là: có khuôn file,
  có chữ ký từng lệnh, có chỗ cắm chính xác vào từng file đang có, có cách kiểm từng phần.
- Trong phạm vi:
  - Thiết kế cho cả sáu hạng mục của bảng `Việc phải làm cho v2`.
  - Khuôn file sơ đồ, đặc tả bằng luật kiểm được chứ không bằng ví dụ.
  - Một file mẫu viết theo đúng khuôn mới, dùng làm bằng chứng khuôn chạy được.
- NGOÀI phạm vi:
  - Sửa bất kỳ file nào trong `scripts/`, `hooks/`, `skills/`, `tests/`. Request này chỉ
    được ghi vào `docs/`. Đây là ranh giới cứng user chốt ở câu 7.
  - Lệnh `dung-nguoc` dựng khung sơ đồ từ đồ thị cho code cũ. Để request sau, vì khuôn chưa
    chạy thật lần nào nên dựng ngược hàng loạt lúc này là nhân bản lỗi khuôn.
  - Dựng sơ đồ cho các tính năng đã có sẵn trong repo. Chỉ áp cho request mới từ nay.
  - Tầng `nhỏ`: miễn hoàn toàn, không phải vẽ sơ đồ.

## 3. Cách tiếp cận & lý do

- Chọn: viết một tài liệu thiết kế duy nhất, kèm một file mẫu chạy thật qua khuôn đó.
- Vì: user chốt output là đề xuất chưa apply, nên giá trị nằm ở chỗ thiết kế đủ chặt để
  request sau khỏi phải quyết định lại. File mẫu là phép thử rẻ nhất cho câu hỏi "khuôn này
  có viết được không" — một khuôn chỉ tồn tại trên giấy thường vỡ ngay lần dùng đầu.
- Đã loại: viết luôn `scripts/tdq_mindmap.py` dạng file đứng riêng — vì user đã trả lời câu
  7 là A, ranh giới cứng là chỉ ghi vào `docs/`.
- Đã loại: cắt làm hai request, thiết kế công cụ trước, thiết kế state machine sau — vì bốn
  hạng mục đầu ràng buộc nhau, tách ra thì phần sau phải đọc lại phần trước.

## 5. Ràng buộc & rủi ro

Ràng buộc kiến trúc phải giữ, chép từ `docs/kien-truc.md`:

- "File code MỚI bắt buộc nằm trong `scripts/` hoặc `hooks/`" — việc này chạm ở chỗ thiết kế
  đặt `tdq_mindmap.py` vào `scripts/`.
- "Chỉ `scripts/tdq_state.py` được ghi `docs/tdq/state.json`" — việc này chạm ở chỗ thiết kế
  gate `diagram_approved`; `tdq_mindmap.py` chỉ được đọc state, không được ghi.
- "`skills/` chỉ được nhắc tên lệnh của `scripts/`, cấm chép nội dung script vào skill" —
  việc này chạm ở chỗ thiết kế skill `tdq-diagram`.
- "Chú thích và docstring trong `scripts/` và `hooks/` viết tiếng Anh cố định" — việc này
  chạm ở các đoạn code mẫu trong tài liệu.

| Rủi ro | Ảnh hưởng | Cách giảm |
|---|---|---|
| Thiết kế trên giấy vỡ khi build thật | request sau phải quay lại sửa thiết kế | viết file mẫu theo đúng khuôn ngay trong request này, khuôn nào không viết nổi thì sửa khuôn tại chỗ |
| Chỗ cắm dẫn sai tên hàm hoặc sai số dòng | request sau tìm không thấy, mất niềm tin vào tài liệu | mỗi chỗ cắm phải đối chiếu lại với file thật trước khi ghi, và ghi tên hàm chứ không chỉ ghi số dòng |
| Tài liệu phình to thành sách | không ai đọc hết, thành ra vô dụng | đặt trần dòng ở §6 và cắt bằng cách bỏ phần diễn giải, giữ phần đặc tả |
| Luật khuôn quá chặt, viết sơ đồ thành cực hình | bước diagram bị người dùng ghét và né | mỗi luật khuôn phải trả lời được câu "luật này bắt lỗi gì có thật", luật nào không trả lời được thì bỏ |
| Chặn phase `qc` gây kẹt request đang chạy | công việc đang dở bị chặn ngang | thiết kế phải nêu rõ cửa thoát, và nêu rõ gate chỉ áp cho request có file sơ đồ |

## 6. QC & Definition of Done

| # | Hạng mục kiểm | Điều kiện PASS |
|---|---|---|
| Q1 | Tài liệu phủ đủ sáu hạng mục | có đúng sáu mục đánh số từ 1 đến 6 trong tài liệu thiết kế |
| Q2 | Mỗi hạng mục nêu được đích | mỗi mục trong sáu mục đó nhắc ít nhất một đường dẫn file trong dấu nháy ngược |
| Q3 | Chữ ký lệnh đầy đủ | có đúng bốn lệnh được đặc tả, mỗi lệnh có tên, đối số và mã thoát |
| Q4 | Luật khuôn phát biểu kiểm được | có ít nhất năm luật khuôn, mỗi luật kèm câu nói rõ nó bắt lỗi gì |
| Q5 | Chỗ cắm dẫn ký hiệu có thật | mọi tên hàm và tên hằng số mà tài liệu dẫn đều tìm thấy trong file được dẫn |
| Q6 | File mẫu qua được khuôn | file mẫu không vi phạm luật khuôn nào phát biểu ở Q4 |
| Q7 | File mẫu có nhánh lỗi | file mẫu chứa ít nhất một dòng đánh dấu nhánh lỗi |
| Q8 | Bảng việc cho request sau | có bảng liệt kê việc, mỗi dòng có file đích và điều kiện xong |
| Q9 | Ranh giới cứng được giữ | không file nào ngoài `docs/` bị thêm hoặc sửa trong request này |
| Q10 | Lint sạch | `doc_lint.py` trên spec, plan và tài liệu thiết kế báo không vi phạm |
| Q11 | Trần độ dài | tài liệu thiết kế không quá 320 dòng |
| Q12 | Nêu cửa thoát của gate | tài liệu nói rõ khi nào gate `qc` KHÔNG áp, và cách gỡ khi bị chặn nhầm |

DoD: đủ mười hai hạng mục Q1 đến Q12 PASS, có bằng chứng ghi trong file QC; hai đầu ra ở §2
tồn tại trên đĩa; không có file nào ngoài `docs/` bị đụng; báo cáo đã viết và đã hỏi user về
việc commit.
