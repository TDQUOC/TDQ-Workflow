- Nguồn: LLVM Coding Standards (áp dụng cho clang/clang-tidy) — https://llvm.org/docs/CodingStandards.html
- Nguồn: C++ Core Guidelines (không tìm được link trực tiếp trong lượt search này, nhưng được nhắc tới gián tiếp; đã biết rộng rãi là isocpp.github.io/CppCoreGuidelines, có clang-tidy check nhóm `cppcoreguidelines-*`) — **chưa verify URL trong lượt search này, cần search bổ sung nếu cần trích dẫn chính xác**.
- Nguồn: PEP 8 – Style Guide for Python Code — https://peps.python.org/pep-0008 (cập nhật lần cuối 2025-04-04, theo trang nguồn)
- Nguồn: Go — Effective Go https://go.dev/doc/effective_go , Go Code Review Comments (qua trích dẫn gián tiếp từ Uber/GDS guide), Google Go Style Guide https://google.github.io/styleguide/go
- Nguồn: GDS Way Go style guide (khuyến nghị linter) — https://gds-way.digital.cabinet-office.gov.uk/manuals/programming-languages/go.html — khuyên dùng `golangci-lint` làm meta-linter, gồm `staticcheck`, `errcheck`, `gosec`, `revive` (golint đã deprecated); `go vet` chạy trong CI.
- Nguồn: Uber Go Style Guide — https://github.com/uber-go/guide/blob/master/style.md — linter tối thiểu khuyến nghị: errcheck, goimports, revive, govet, staticcheck.
- Nguồn: Rust API Guidelines + clippy (qua thảo luận cộng đồng) — https://users.rust-lang.org/t/is-there-something-like-rust-core-guidelines-like-c-core-guidelines/113850 — Rust không có "Core Guidelines" tương đương C++; triết lý Rust là để compiler + `cargo clippy` (hàng trăm lint) và `rustfmt` thực thi convention thay vì văn bản mô tả; "Rust API Guidelines" là tài liệu gần nhất.
- Nguồn TypeScript/JS, HTML: **không tìm đủ nguồn xác thực trong 2 lượt search** (tìm ESLint/typescript-eslint recommended config, htmlhint, W3C validator nhưng kết quả trả về không bám sát câu hỏi này — cần thêm 1 lượt search chuyên biệt nếu muốn trích dẫn URL chính xác cho TS/HTML).
- Rút ra chung: mỗi ngôn ngữ có 2 lớp nguồn tách biệt — (a) style guide văn bản (PEP8, Effective Go, C# Coding Conventions, C++ Core Guidelines) và (b) linter/analyzer thực thi tự động (ruff/Roslyn/clang-tidy/golangci-lint/clippy) — rule library nên map 1-1 giữa khái niệm trong style guide và rule ID của linter tương ứng để agent có thể trích dẫn cụ thể.

## Truy vấn 2: Codify "technical debt" thành phép kiểm tự động (SonarQube, CISQ, ISO 25010)
- Nguồn: Sonar Community — "Introducing Clean Code in our products" — https://community.sonarsource.com/t/introducing-clean-code-in-our-products/98431 — Clean Code = 4 thuộc tính đo được: Consistent, Intentional, Adaptable, Responsible; mỗi issue gắn với 1 attribute + mức độ ảnh hưởng (low/medium/high) lên 3 "software qualities": Security, Reliability, Maintainability.
- Nguồn: arXiv 2411.10656 (nghiên cứu định lượng LLM code quality bằng SonarQube) — https://arxiv.org/html/2411.10656v2 — trên 1.848 issue thực tế: 59.6% do Intentionality, 31.2% do Consistency, 9.4% do Adaptability, 0% do Responsibility → Intentionality (đặt tên rõ, logic đầy đủ, không code chết) là nhóm áp đảo nhất khi LLM sinh code.
- Nguồn: SonarSource — "What are quality gates" — https://www.sonarsource.com/resources/library/quality-gate — quality gate mặc định "Sonar way" chỉ áp cho code mới (New Code), không bắt sửa nợ cũ ngay.
- Nguồn: khimananda.com — SonarQube Quality Gate Guide 2026 — https://khimananda.com/blog/sonarqube-code-quality-and-security-gates — ngưỡng phổ biến: Security Rating = A; Reliability Rating ≥ B; Maintainability Rating = A (technical debt ratio < 5%); Coverage on New Code ≥ 80%; Duplicated Lines on New Code ≤ 3%.
- Nguồn: objectscriptquality.com — https://objectscriptquality.com/article/quality-gate-what-and-how-configure-it — khuyên tách riêng quality gate cho dự án legacy vs dự án mới.
- Rút ra: "nợ kỹ thuật" có thể đo bằng 5 con số cụ thể (coverage %, duplication %, technical debt ratio %, số bug/vulnerability mới = 0, complexity). CISQ/ISO 25010 được nhắc đến trong câu hỏi nhưng **không xuất hiện nguồn cụ thể trong kết quả search** — không tìm được nguồn cho mapping CISQ/ISO 25010 chi tiết, cần search riêng nếu cần.

## Truy vấn 3: Taxonomy chung cho mọi ngôn ngữ (SOLID, CERT, OWASP, complexity)
- Nguồn: Sonar rule "brain-overload" tag + Trimble Dev Guidelines — https://devguide.trimble.com/development-practices/managing-code-complexity — cyclomatic complexity: <10 = đơn giản, >20 = quá phức tạp, khuyến nghị ngưỡng chấp nhận trong khoảng 10-20 tuỳ domain; cognitive complexity đo được bằng SonarQube/SonarLint cho C#, JS/TS (`eslint-plugin-sonarjs`), Java, Python, Go.
- Nguồn: DevIQ — Cognitive Complexity — https://deviq.com/terms/cognitive-complexity — metric do G. Ann Campbell (SonarSource) công bố 2018, phạt nesting và flow-breaking construct, khác cyclomatic complexity (đếm path).
- Nguồn: dev.to (optiklab) — https://dev.to/optiklab/writing-self-documented-code-with-low-cognitive-complexity-3k2l — ngưỡng mặc định SonarQube: Cognitive Complexity = 15 (đa số ngôn ngữ), 25 (họ C: C/C++/Objective-C); Cyclomatic Complexity = 10 (mọi ngôn ngữ).
- Nguồn: Augment Code — https://www.augmentcode.com/learn/how-to-reduce-cyclomatic-complexity — bảng so sánh ngưỡng mặc định theo tool: ESLint `complexity` mặc định 20 (nhiều team hạ xuống 10-15); Microsoft CA1502 mặc định 25; NIST SP 500-235 dùng 10 làm mốc tham chiếu gốc (McCabe 1976); gocyclo không có default chung, tuỳ team.
- Nguồn: Kiuwan — CERT & OWASP — https://www.kiuwan.com/blog/secure-coding-guidelines — SEI CERT (Carnegie Mellon) chia rule theo category viết tắt (MSC, EXP, MEM…) có severity + enforceability; OWASP Secure Coding Practices Quick Reference Guide là checklist **ngôn ngữ-trung lập** (language-agnostic) — đây là ứng viên tốt nhất cho tầng "chung mọi ngôn ngữ" về bảo mật.
- Rút ra: taxonomy chung khả thi nhất gồm 2 trục độc lập ngôn ngữ — (1) độ phức tạp: cyclomatic ≤10 (khuyến nghị phổ biến, gốc McCabe 1976) + cognitive ≤15 (≤25 cho họ C), và (2) bảo mật: OWASP Secure Coding Practices (checklist chung) + CERT (khi ngôn ngữ có bộ CERT riêng: C, C++, Java, Perl). SOLID được nhắc đến (Trimble cite Chidamber & Kemerer 1994) nhưng không có ngưỡng số đo trực tiếp — SOLID là nguyên tắc thiết kế định tính, không phải rule tự động hoá được như complexity.

## Truy vấn 4: Cách viết rule cho AGENT/LLM đọc (không phải cho người)
- Nguồn: HumanLayer — "Writing a good CLAUDE.md" — https://www.humanlayer.dev/blog/writing-a-good-claude-md (2025-11-25) — LLM là stateless, CLAUDE.md/AGENTS.md là file DUY NHẤT nạp vào MỌI conversation → phải universal, không chứa hướng dẫn theo tình huống cụ thể; độ dài khuyến nghị: **dưới 300 dòng, càng ngắn càng tốt** (ví dụ thực tế: HumanLayer root CLAUDE.md < 60 dòng); nhấn mạnh Progressive Disclosure — chỉ nạp chi tiết khi cần, không nhồi hết vào 1 file.
- Nguồn: BuildBetter.ai — "AGENTS.md vs .cursorrules vs Claude Skills: 2026 Guide" — https://blog.buildbetter.ai/agents-md-vs-cursorrules-vs-claude-skills-2026-comparison — khuyến nghị độ dài AGENTS.md: **500-2.000 token (~1-3 trang)**, vì mọi token bị nạp ở MỌI lần agent chạy; nên link ra tài liệu sâu (CONTRIBUTING.md, ADR) thay vì inline; `.cursorrules` (file đơn) coi như deprecated, Cursor khuyên chuyển sang `.cursor/rules/*.mdc` (có scoping + file-pattern trigger); layered model 2026: AGENTS.md = ambient context, Skills = workflow có thể invoke theo nhu cầu, MCP = data access — 3 lớp bổ sung nhau, không cạnh tranh.
- Nguồn: dev.to (mcsee) — "AI Coding Tip 013 - Use Progressive Disclosure" — https://dev.to/mcsee/ai-coding-tip-013-use-progressive-disclosure-102a — ví dụ cụ thể: SKILL.md monolithic 15.000 token buộc AI nạp toàn bộ dù chỉ hỏi 1 rule nhỏ; SKILL.md modular 800 token + file con theo chủ đề (vd `declaration.md` 1.200 token) chỉ nạp khi từ khoá khớp — mô hình 3 giai đoạn: Discovery (chỉ tên+mô tả) → Activation (nạp SKILL.md đầy đủ khi khớp) → Execution (nạp file tham chiếu/script chỉ khi thật sự cần).
- Nguồn: towardsai.net — https://pub.towardsai.net/ai-agents-skills-hooks-tool-standards-acdda0510a68 — cơ chế discovery của Claude Code skill: quét metadata (~100 token: tên + description) trước, chỉ nạp full instructions khi task khớp mô tả.
- Nguồn: GitHub ciembor/agent-rules-books — https://github.com/ciembor/agent-rules-books — thực hành: đóng gói MỖI bộ rule thành 3 bản riêng — `mini` (dùng thực tế hàng ngày), `nano` (khi context budget rất hẹp), `full` (bản gốc đầy đủ, tham chiếu) — đúng mô hình progressive disclosure áp cho rule-set kỹ thuật (không chỉ prose).
- Nguồn: Medium (alexefimenko) — https://medium.com/@alexefimenko/your-ai-coding-agent-is-only-as-good-as-its-rules-heres-how-to-write-ones-that-actually-work-f6bceb564871 — cảnh báo: rule kiểu "Improve Codebase" (mơ hồ, định tính) không nên là AI rule — nên là ESLint rule/Prettier config/tsconfig flag/CI check thay vì rule bằng lời cho agent tự diễn giải; ví dụ thực tế: trim CLAUDE.md từ 200+ dòng xuống ~80 dòng giúp agent làm việc tốt hơn rõ rệt.
- Rút ra: (1) rule cho agent phải cụ thể, có thể verify bằng lệnh, không phải mô tả định tính; (2) tổ chức 2-3 tầng nạp (metadata mỏng → nội dung đầy đủ khi khớp → reference sâu khi cần) đúng cấu trúc Claude Code skill hiện tại (SKILL.md + references/); (3) mỗi file rule nên gọn (khuyến nghị chung: vài trăm đến ~2.000 token/rule-set con), tách theo ngôn ngữ hoặc theo category thay vì 1 file khổng lồ.

## Tổng hợp
Đã chắc: (1) Mỗi ngôn ngữ đều có cặp nguồn style-guide + linter/analyzer mặc định rõ ràng, có thể trích rule ID cụ thể (Roslyn category, ruff/PEP8, clippy, staticcheck/govet, clang-tidy) — riêng TS/JS và HTML cần search bổ sung để có URL chính xác. (2) SonarQube Clean Code taxonomy (Consistent/Intentional/Adaptable/Responsible) là khung phân loại issue thực dụng nhất hiện có, và dữ liệu thực nghiệm (arXiv 2411.10656) cho thấy code LLM sinh ra lỗi chủ yếu ở Intentionality (59.6%) — nên ưu tiên rule nhóm này (đặt tên, code chết, logic không đầy đủ). (3) Ngưỡng complexity có sự đồng thuận tương đối: cyclomatic complexity ≤10 (gốc McCabe 1976, NIST SP 500-235 dùng làm mốc), cognitive complexity ≤15 (≤25 cho họ ngôn ngữ C) là ngưỡng mặc định SonarQube phổ biến nhất — nhưng ESLint/Microsoft CA1502 có default khác (20, 25) nên "ngưỡng chuẩn" thực ra là do tool/team chọn, không có một số tuyệt đối. (4) Với rule cho AI agent: đồng thuận mạnh là ngắn, cụ thể, verify được bằng lệnh, và nạp theo progressive disclosure 2-3 tầng (giống cấu trúc SKILL.md + references/ đã có trong plugin TDQ) — độ dài tầng "luôn nạp" nên dưới vài trăm dòng/token, chi tiết đẩy xuống references chỉ nạp khi cần.

Mâu thuẫn/chưa rõ giữa nguồn: ngưỡng cyclomatic/cognitive complexity KHÔNG thống nhất tuyệt đối giữa các tool (10 vs 15-20 vs 25 tuỳ nguồn) — cần chốt một ngưỡng làm mặc định cho thư viện rule TDQ và cho phép override.

Không tìm được nguồn: (a) CISQ và ISO 25010 mapping chi tiết sang phép đo cụ thể; (b) URL chính thức xác thực cho C++ Core Guidelines trong lượt search này (dù được biết rộng rãi qua tên); (c) nguồn xác thực cho ESLint/typescript-eslint recommended ruleset và htmlhint/W3C validator cho HTML — cần thêm 1 lượt search riêng nếu người chủ trì cần trích dẫn chính xác cho 2 mục này.

## Truy vấn 5: Bù 3 khoảng trống nguồn (T4.1 — tavily advanced, truy cập 2026-08-14)
- Nguồn TS/JS: typescript-eslint — "Shared Configs" — https://typescript-eslint.io/users/configs (docs hiện hành, truy cập 2026) — bộ `recommended` = rule bắt lỗi đúng đắn (correctness) drop-in không cần config thêm; tầng nâng dần `recommended` → `strict` → `stylistic`; kèm danh mục rule đầy đủ có đánh dấu ✅ recommended tại https://typescript-eslint.io/rules và rule core JS tại https://eslint.org/docs/latest/rules (ESLint docs latest, 2026).
- Nguồn HTML: W3C Markup Validation Service — https://validator.w3.org/ (bản quyền W3C 2024, đang chạy) — validator chính thức của W3C cho HTML/XHTML, có bản Nu không dựa DTD tại https://validator.w3.org/nu; linter CLI: HTMLHint — danh mục rule chính thức https://htmlhint.com/rules/ (docs hiện hành 2026, vd `doctype-first`, `doctype-html5`, `head-script-disabled`), chạy được qua lệnh `htmlhint` nếu máy đã cài.
- Nguồn C++: repo chính thức C++ Core Guidelines — https://github.com/isocpp/CppCoreGuidelines (org isocpp; commit gần nhất của hsutter 2026-08-06 — dự án đang sống) — do Bjarne Stroustrup công bố tại CppCon 2015-09-21, nguồn công bố: https://isocpp.org/blog/2015/09/bjarne-stroustrup-announces-cpp-core-guidelines (2015); guideline nhắm rule máy-enforce được (qua clang-tidy nhóm `cppcoreguidelines-*`), tập trung interface, resource/memory management, concurrency.
- Rút ra: lấp xong khoảng trống (b) và (c) ở mục "Không tìm được nguồn" phía trên — cả 3 mục đều có URL chính thức + năm, đủ căn cứ trích dẫn cho `rules/typescript-js.md`, `rules/html.md`, `rules/cpp.md`.
